# blind — план Rust TUI-харнесса со сверхстрогими агентами

> Имя — `blind`: агент видит только то, что ему разрешено.
> Основа: `agent-protocol` (Go, `github.com/igorrize/agent-protocol`) и pi-плагин (по `PLAN-PI.md`). Исполняется по
> этапам §14.
>
> Статус: v5, 2026-11-15 · M0 готов; выбраны зависимости (§10.3); ollama.com среди провайдеров (§7.2); контракт в
> v1 — голый JSON, свой DSL отложен (§4.6).

---

## 0. Коротко

- **Харнесс сам крутит цикл агента и не привязан к модели.** Он ходит в API любой модели — Anthropic, OpenAI и всё
  OpenAI-совместимое (OpenRouter, Gemini, облачный ollama.com, локальные Ollama, LM Studio, vLLM) — и сам исполняет
  вызовы инструментов.
  Модель может только попросить инструмент из своего гранта; другого пути к ОС у неё нет, с любым провайдером.
  В Go-версии замок держался на флагах `claude`.
- **MCP — с той же строгостью, в трёх ролях.** Воркерам — инструменты MCP-серверов по allowlist, stdio-серверы в
  песочнице. Внешний агент за MCP — лист дерева со строгим входом и выходом. Наружу — `blind mcp serve`: внешние
  клиенты вызывают агентов blind как MCP-инструменты.
- **Координаторы умеют только вызывать агентов.** Root-агент (с ним говорит пользователь) и все промежуточные агенты
  получают только инструменты `agent_<имя>`, по одному на каждого разрешённого саб-агента; схема входа берётся из его
  контракта. Ни файлов, ни shell, ни сети.
- **Работают только листья-воркеры:** инструменты из контракта, скоупы путей, ОС-песочница. Пишут они только в
  одноразовую копию; в рабочее дерево патч применяет человек.
- **Права только сужаются вниз по дереву.** Ребёнок получает «контракт ∩ сужение от родителя», бюджет резервируется
  из остатка родителя, граф вызовов — DAG с лимитом глубины.
- **Правила пишет только человек.** Регистрации агентов в рантайме нет. Контракты лежат файлами, закреплены хешем и
  одобряются в TUI; агенты не могут их менять.
- **Интерфейс:** сайдбар (агенты, окна, сессии) и вкладки. Вызванный агент сам получает вкладку — в фоне, фокус не
  прыгает. Быстрый переход по `Ctrl-X p`, логи — отдельной вкладкой и панелью внизу. Раскладка, клавиши и тема
  настраиваются.

## 1. Обзор

### 1.1 Цели

- **G1.** TUI: сайдбар и вкладки, своя вкладка у каждого агента, быстрое переключение между агентами и окнами, логи,
  настраиваемая раскладка.
- **G2.** Агенты и саб-агенты по контрактам («правилам»): типизированный вход и выход (JSON Schema), инструменты,
  скоупы путей, лимиты, граф вызовов `can_call`.
- **G3.** Сверхстрогая изоляция: инструменты по гранту + скоупы ФС + ОС-песочница + бюджеты. Везде fail-closed.
- **G4.** Любые модели по API. Строгость не зависит от провайдера.
- **G5.** MCP с той же строгостью: инструменты для воркеров по allowlist, внешние агенты за MCP как листья дерева и
  blind как MCP-сервер для внешних клиентов.
- **G6.** Полный аудит и логи: каждое решение (разрешено, заблокировано, отклонено, одобрено) пишется в append-only
  журнал с цепочкой хешей.
- **G7.** Детерминированные тесты всей системы без сети (mock-провайдер) и набор попыток побега из песочницы в CI.
- **G8.** macOS и Linux, установка через существующий Homebrew-тап.

### 1.2 Не-цели v1

- **N1.** Плагины, skills, расширения UI. Новые возможности появляются только в закрытом каталоге (§5.1) или через MCP
  по allowlist (§5.7).
- **N2.** Чужие CLI (`claude`, `pi`) в роли воркеров. Возможно позже (§16).
- **N3.** Windows.
- **N4.** Возобновление задач после перезапуска. Журнал и транскрипты пишутся, но при выходе незавершённые задачи
  отменяются.
- **N5.** Защита от подменённого бинарника харнесса и уязвимостей ядра ОС.

### 1.3 Решения по умолчанию (подтвердить в §17)

| Вопрос | По умолчанию |
|---|---|
| Кто крутит цикл агента | сам харнесс |
| Модели | любые через адаптеры: Anthropic и OpenAI-совместимые API (OpenAI, OpenRouter, Gemini, ollama.com, локальные); в контракте — `провайдер/модель`, значение по умолчанию — в конфиге пользователя |
| MCP | три роли: инструменты воркеров по allowlist; внешний агент за MCP как лист дерева (`kind = "external"`); наружу — `blind mcp serve` |

| Root | чистый координатор, без чтения файлов |
| Запись в ФС | только в одноразовую копию; в рабочее дерево — патч после одобрения человеком |

| Формат правил | JSON-контракт: строгий профиль JSON Schema, разобранный в Rust-типы; свой DSL отложен (§4.6); импорт старых `contract.json` |

## 2. Что берём из agent-protocol и что чиним

### 2.1 Берём

- **Контракт = правило:** схемы входа и выхода плюс инструменты (`examples/*/contract.json`).
- **Валидация на обоих концах:** params при вызове, output при `complete`
  (`internal/app/usecases/dispatch.go`, `internal/app/usecases/complete.go`).
- **Исходы — значения, а не исключения:** `dispatched / rejected / no_such_agent / blocked / completed / error`
  (`internal/app/ports/errors.go`, `internal/app/adapters/mcp/errmap.go`). «Отклонено — исправь и повтори»
  отличается от «стоп».
- **Инструменты по роли** (`roleTools` в `internal/app/adapters/mcp/tools.go`) и **whitelist вместо blocklist**
  (README, раздел Locking).
- **Агенты как MCP-инструменты** — идея прокси; в blind она живёт в `blind mcp serve` (§6.6).
- **Аудит-кольцо** (`internal/app/adapters/audit/ring.go`) и гексагональная схема ports/adapters с чистым ядром,
  как и в `PLAN-PI.md`.

### 2.3 Сравнение

| | agent-protocol (Go) | pi-плагин (по `PLAN-PI.md`) | blind |
|---|---|---|---|
| Цикл агента | Claude Code CLI | pi | сам харнесс |
| Модели | Claude (через CLI) | модели pi | любые по API, задаются в контракте |
| MCP | сам прокси — MCP-сервер | нет | инструменты воркеров по allowlist, внешние агенты за MCP, `blind mcp serve` |

| Канал между агентами | HTTP MCP на `:4321` + bearer | UDS + bearer | внутри процесса, только типизированный |
| Иерархия | плоская | плоская | дерево, граф `can_call` |
| Права ребёнка | `allowed_tools` контракта | то же | контракт ∩ сужение, бюджет из остатка родителя |
| Регистрация агентов | `register` в рантайме | то же | только человек, закреплено хешем |
| Скоупы ФС | нет | нет | глобы + `cap-std` + ОС |
| ОС-песочница | нет | нет (guardrails) | Seatbelt / Landlock + seccomp |
| Валидация | подмножество JSON Schema, верхний уровень | то же | полная JSON Schema в харнессе; strict-режим провайдера — где есть |
| Запись в репо | напрямую | напрямую | только патч через одобрение |

## 3. Принципы

1. **Харнесс — единственный исполнитель, с любой моделью.** Модель производит только текст и вызовы инструментов.
   Исполняется лишь то, что есть в гранте; всё остальное — `blocked` и запись в аудит.
2. **Только whitelist, везде fail-closed.** Неизвестный инструмент, поле конфига, тип в схеме, неподтверждённая
   возможность модели, недоступная песочница — отказ, а не предупреждение.
3. **Разделение обязанностей.** Root только разговаривает и формулирует задания, воркер только работает, а куда идёт
   работа, решают объявленные переходы и человек. Модель маршрут не выбирает.
4. **Права только сужаются.** Никто ниже по дереву не получает больше, чем выше: инструменты, скоупы, бюджет, глубина.
5. **Правила пишет человек.** Агенты не создают и не меняют контракты; доверие — по хешу, хранится вне репозитория.
6. **Две стены.** Тонкая проверка в Rust (глобы, deny) и грубая в ОС (Seatbelt, Landlock). Ошибка в одной не
   открывает другую.
7. **Только типизированные каналы.** Ребёнок видит только свои params, родитель — только провалидированный output
   ребёнка. Сиблинги не общаются.
8. **Изменения — через человека.** Воркеры пишут в одноразовую копию; патч в рабочее дерево применяет человек.
9. **Всё в аудит и логи.** Append-only, цепочка хешей, без секретов.
10. **Чистое ядро, тонкие адаптеры** — как в Go-версии и `PLAN-PI.md`. Провайдеры, MCP, ФС и TUI — адаптеры вокруг
    ядра; исходы — enum с исчерпывающим `match`.

## 4. Агенты и правила

### 4.1 Виды агентов

| Вид | Что делает | Права | Куда идёт результат |
|---|---|---|---|
| `root` | один на сессию: разговаривает с человеком и обсуждает итоги; на пути работы не стоит | только смотреть: чтение проекта и веб-поиск; писать не может | итог цепочки возвращается ему |
| `worker` | делает одну работу по наряду: вход → работа → output, контекст потом выбрасывается | только из своего контракта | по объявленным переходам (§4.7) |
| `external` | внешний агент за MCP; харнесс видит только вход и выход (§5.8) | внутри — вне нашего контроля; stdio — в песочнице | по объявленным переходам |

```rust
pub enum AgentKind {
    Root,
    Worker   { tools: ToolSet, fs: FsPolicy, exec: Option<ExecPolicy>, mcp: Vec<McpGrant> },
    External { endpoint: McpEndpoint, tool: ToolName, fs: Option<FsPolicy>, network: bool },
}
```

Выбирать, кого звать, некому: маршрут задают переходы (§4.7). Шаг «подумать и разбить задачу» — обычный `worker` без
прав, его output становится входом следующих узлов.

Разделы 4.2–6 и 15 местами ещё описывают координатора — они будут переписаны вместе с черновиком грамматики DSL.

### 4.2 Файлы

**Что реализовано (M1, 2026-11-20).** Пара — папка `.blind/agents/<имя>/` с тремя файлами:

- `contract.json` — железное: `name`, `kind` (пока только `worker`), `input`, `output`, `rights` (`read`, `write`);
- `agent.json` — мягкое: `description`, `model` (`провайдер/модель`);
- `prompt.md` — инструкция агенту.

Имя папки должно совпадать с `name` в контракте. Проверка — `blind agent check [--dir <папка>]`; примеры лежат в
`examples/agents/`. TOML-примеры ниже в этом разделе устарели и будут переписаны.

```
~/.config/blind/                  # у пользователя, не в репозитории
├── providers.toml                 # провайдеры, ключи, возможности моделей, цены (§7.2)
├── harness.toml                   # потолки лимитов; проектный harness.toml может только ужесточать
└── ui.toml                        # раскладка, клавиши, тема (§8.5)

<проект>/.blind/
├── harness.toml                   # root, лимиты сессии, разрешённые модели, mcp_server
└── agents/
    ├── lead/          agent.toml · prompt.md · input.schema.json · output.schema.json
    └── clj-reviewer/  agent.toml · prompt.md · input.schema.json · output.schema.json
```

Доверие хранится вне репозитория (§4.5).

**`.blind/harness.toml`:**

```toml
[root]
model    = "anthropic/claude-opus-5-5"   # любая пара провайдер/модель из providers.toml
can_call = ["lead", "explorer"]

[limits]
max_depth          = 3        # длина самой длинной цепочки вызовов от root
max_agents_total   = 32       # агентов за сессию
max_concurrent     = 4        # одновременно работающих агентов
session_budget_usd = 5.00

[models]
allow = ["anthropic/*", "local/*"]   # какие модели вообще можно указывать в контрактах проекта

[mcp_server]                          # для `blind mcp serve` (§6.6)
can_call   = ["explorer", "clj-reviewer"]
budget_usd = 1.00

[sandbox]
mode = "required"             # required | degraded (только чтение через cap-std, без записи и exec)
```

**Воркер:**

```toml
# .blind/agents/clj-reviewer/agent.toml
name         = "clj-reviewer"
kind         = "worker"
description  = "Ревьюит Clojure-файлы по рубрике. Вызывай, когда нужны замечания, а не правки."
model        = "local/qwen2.5-coder:14b"   # провайдер `local` из providers.toml; делим по первому «/»
prompt       = "prompt.md"
input        = "input.schema.json"
output       = "output.schema.json"
instructions = false            # только типизированные params, без свободного текста от родителя

[tools]
read_file = {}
glob      = {}
grep      = { max_results = 200 }

[fs]
read = ["src/**", "test/**"]
deny = ["src/secrets/**"]       # добавляется к неотключаемому hard-deny (§5.3)

[limits]
max_turns      = 30
max_tool_calls = 120
max_tokens     = 400000         # для локальной модели денежный бюджет не имеет смысла — ограничиваем токены
timeout        = "10m"
```

**Координатор:**

```toml
# .blind/agents/lead/agent.toml
name         = "lead"
kind         = "coordinator"
description  = "Делит задачу «ревью + тесты» между ревьюером и автором тестов."
model        = "anthropic/claude-opus-5-5"
reasoning    = "high"           # маппится на параметр провайдера; модель без поддержки → ошибка загрузки
prompt       = "prompt.md"
input        = "input.schema.json"
output       = "output.schema.json"
can_call     = ["clj-reviewer", "clj-test-writer"]
min_children = 1

[calls.clj-reviewer]
fs.read = ["src/**"]            # статическое сужение: этот ребёнок, вызванный отсюда, видит только src/

[limits]
max_parallel = 3
max_children = 6
max_cost_usd = 2.00
timeout      = "30m"
```

**Что из этого видит модель координатора** — сгенерированный инструмент (форма — нейтральная, адаптер провайдера
переводит её в свой формат):

```json
{
  "name": "agent_clj-reviewer",
  "description": "Ревьюит Clojure-файлы по рубрике. Вызывай, когда нужны замечания, а не правки. Возвращает {summary, findings}. Работает изолированным саб-агентом и видит только переданные params.",
  "strict": true,
  "input_schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["files", "rubric"],
    "properties": {
      "files":  { "type": "array", "items": { "type": "string" } },
      "rubric": { "type": "string" }
    }
  }
}
```

`strict` уходит провайдеру, только если модель это умеет (§7.3). Если контракт разрешает `instructions = true`, к
схеме добавляется необязательная строка `instructions` с лимитом длины; поле с таким именем в самой схеме контракта
запрещено.

### 4.3 Импорт `contract.json` из Go-версии

`blind agent import examples/` превращает каждый `contract.json` в `agent.toml` и файлы схем. Импортированные агенты
проходят одобрение, как любые новые.

| Go / Claude Code | blind |
|---|---|
| `Read` | `read_file`; скоуп по умолчанию — весь проект минус hard-deny |
| `Glob`, `LS` | `glob`, `list_dir` |
| `Grep` | `grep` |
| `Write`, `Edit` | `write_file`, `edit_file` (только в копию, §5.4) |
| `Bash` и всё прочее | ошибка импорта; `exec` описывается явно |

Модель при импорте не угадывается: берётся значение по умолчанию из конфига пользователя. Импорт предупреждает о
слабых схемах (массив без `items`, объект без `properties`): там строгость стоит дотянуть руками.

### 4.4 Проверки при загрузке

Каждая — ошибка загрузки, не предупреждение:

1. Неизвестные поля в `agent.toml` и `harness.toml` (`serde(deny_unknown_fields)`).
2. Координатор с `[tools]`, `[fs]` или `[mcp]`; воркер с `can_call`; внешний агент с `[tools]`, `[mcp]` или `can_call`.
3. `can_call` ссылается на неизвестного или неодобренного агента.
4. Граф `can_call` вместе с root — DAG; самый длинный путь ≤ `max_depth`.
5. Схемы компилируются (JSON Schema 2020-12), корень — `object`, рекурсии нет, схема понижается под профиль
   провайдера модели (§7.4).
6. Инструменты — только из каталога §5.1 и MCP-allowlist; скоупы внутри корня проекта; hard-deny не переопределяется.
7. Модель — из `[models] allow`, а её подтверждённые возможности (§7.3) покрывают то, что нужно агенту: tool calling
   у координаторов и воркеров с инструментами, `reasoning` — если он указан, usage — если задан бюджет в токенах или
   деньгах.
8. Лимиты агента не выше потолков сессии.
9. Имя агента — `[a-z0-9-]`, не длиннее 48 символов: `agent_<имя>` проходит ограничения провайдеров на имена
   инструментов.

### 4.5 Доверие

- Контракт (все его файлы) хешируется (`blake3`). Одобренные хеши лежат в каталоге состояния пользователя
  (`<state>/trust/<id-проекта>.json`), вне репозитория: репо не может «одобрить себя».
- Новый или изменённый контракт → экран одобрения в TUI: вид, модель, инструменты, скоупы, MCP-инструменты с
  описаниями, `can_call`, лимиты, diff с прошлой версией. Пока контракт не одобрен, агента нет: у родителей нет
  инструмента для его вызова.
- `harness.toml` проекта проходит то же одобрение.
- CLI: `blind agent new <имя>` (скаффолд), `blind agent check` (все проверки §4.4 и граф), `blind agent trust`
  (одобрение без TUI), `blind agent import <каталог>`.

`<state>` — каталог состояния пользователя: `$XDG_STATE_HOME/blind` на Linux, `~/Library/Application Support/blind`
на macOS.

### 4.6 Свой DSL контрактов — отложен

Решение 2026-11-20: в v1 контракт — голый JSON (строгий профиль JSON Schema, разобранный в Rust-типы). К DSL
вернёмся позже; ниже — что он мог бы дать.

JSON и YAML со схемой описывают форму одного сообщения. DSL с проверяющим компилятором проверяет граф агентов
целиком: откуда берутся данные, куда им можно течь, какие права едут вместе с ними и в каком порядке идут вызовы. Он
мог бы дать шесть проверок:

1. **Происхождение output.** Поле output координатора можно привязать к output ребёнка (`findings = reviewer.findings`):
   его заполняет харнесс, модель координатора его не пишет и выдумать не может.
2. **Метки доверия.** Значения из файлов и ответов MCP помечены как недоверенные (`text<untrusted>`). Компилятор не
   пускает их в system prompt, `instructions`, argv `exec` и пути для записи — по всему графу, ещё при загрузке.
3. **Права внутри типов.** `path<read …>`, `path<write …>` — право едет вместе со значением. Ребёнок пишет только в
   переданные ему пути; передать право может только тот, у кого оно есть.
4. **Протокол вызовов.** Порядок и число вызовов — конечный автомат (`reviewer -> test_writer? -> done`), вызов вне
   протокола харнесс отклоняет. Поле output, привязанное к необязательному вызову, обязано быть необязательным.
5. **Детерминированные шаги.** Шаги, где решать нечего, исполняет харнесс без модели. Выражения — часть грамматики и
   проверяются по типам при загрузке, а не строки, как в YAML-пайплайнах.
6. **Типизированные шаблоны промптов.** Подстановки сверяются со схемой при загрузке; недоверенные данные нельзя
   подставить в system prompt.

Плюс сама грамматика: нет неявных типов YAML (`NO` → `false`) и молчаливых дубликатов ключей JSON.

Что остаётся за JSON Schema: компилятор генерирует её для провайдеров (с понижением под профиль, §7.4); схемы чужих
MCP-инструментов проверяются как есть; `contract.json` из Go-версии импортируется.

Набросок синтаксиса, не финал:

```
agent lead: coordinator {
  input    { files: [path<read src/**>] max 50, target: path<write test/**> }
  protocol reviewer -> test_writer? -> done
  output {
    findings = reviewer.findings
    tests?   = test_writer.test_file
    summary: text max 500
  }
}
```

### 4.7 Переходы: куда идёт работа, решает не модель

- Модель только работает внутри своего узла. Куда пойдёт её output, объявлено рядом с промптом (не в тексте промпта),
  и переход исполняет харнесс.
- Три вида переходов:
  1. **жёсткий** — всегда в один узел;
  2. **по условию** на провалидированный output — условие проверяет харнесс;
  3. **выбор человеком в TUI** — от 1 до 4 вариантов (больше — ошибка компилятора), подписи берутся из `description`
     агентов.
- Выборы ветвятся. Путь можно запомнить на следующие N задач: это состояние сессии, а не контракт. Каждый автовыбор
  пишется в аудит; развилка, которой нет в памяти, — снова вопрос человеку.
- Без человека (`blind run`, `blind mcp serve`) развилка без запомненного пути — остановка «нужен выбор».
- **Цепочку на задачу строит человек** в TUI по хоткею: список воркеров (параллельно) или порядок (последовательно).
  Несовместимые шаги (output одного не покрывает input следующего) сборщик не даёт добавить и объясняет почему.
  Без цепочки промпт — просто разговор с root, работа не начинается. Готовые цепочки сохраняются и вызываются одной
  клавишей.
- Цепочку можно собрать из любых воркеров, совместимых по типам; разрешение на связь в контрактах не нужно.
- **Задание — это промпт человека.** Каждый шаг получает его как текст `task` с меткой «от человека»; типизированные
  поля шаг берёт из output предыдущего шага. Ничего не подтверждается: промпт и цепочка — и всё.
- Первым в цепочке может стоять только воркер, которому на вход хватает `task`. Того, кому нужны поля от предыдущего
  шага, сборщик первым поставить не даст.
- **Оркестратор — это сам харнесс, а не модель.** Шаги идут по очереди, output шага уходит на вход следующему. В
  параллельной группе дети друг друга не видят и не общаются; харнесс собирает их output и передаёт следующему шагу
  списком, а после последнего шага — в root.
- **Root** — единственный, кто рассуждает и долго разговаривает: диалог с человеком, большой контекст. Смотреть
  может (чтение проекта, веб-поиск), писать — нет. На пути работы он не стоит: задание и цепочку даёт человек, а root получает итог в конце цепочки и
  обсуждает его. Транскрипты узлов он не видит, только их провалидированный output.

## 5. Возможности

### 5.1 Закрытый каталог инструментов v1

| Инструмент | Кому | Что делает | Ограничения |
|---|---|---|---|
| `agent_<имя>` | root, координатор | вызывает саб-агента; вход — input-схема его контракта; результат — его провалидированный output | только имена из `can_call` |
| `complete` | все, кроме root | завершает задачу; вход — output-схема контракта | единственный вызов в своём ходе |
| `read_file` | воркер | читает файл или диапазон строк | скоуп `fs.read`, лимит размера, бинарные файлы — отказ |
| `list_dir`, `glob` | воркер | листинг и поиск путей | скоуп `fs.read`, учитывает `.gitignore`, лимит результатов |
| `grep` | воркер | поиск по содержимому (движок ripgrep) | скоуп `fs.read`, лимит результатов |
| `write_file`, `edit_file` | воркер | пишет и правит файлы в своей копии | скоуп `fs.write`, только копия (§5.4) |
| `exec` | воркер | запускает программу | argv из allowlist, без shell, в песочнице (§5.5) |
| `mcp_<сервер>_<инструмент>` | воркер | вызывает инструмент MCP-сервера | только из allowlist контракта, хеш описания закреплён (§5.7) |

Нет: shell-строк, прямой сети, веба, `register`, чтения аудита и транскриптов других агентов.

### 5.2 Грант и сужение

```rust
pub struct Grant { /* поля приватные: собрать можно только через root() и derive_child() */ }

impl Grant {
    pub fn root(cfg: &HarnessConfig) -> Grant;
    /// Ребёнок = контракт ∩ сужение от родителя; бюджет — резерв из остатка родителя.
    pub fn derive_child(&self, child: &Contract, narrowing: &Narrowing) -> Result<Grant, Denied>;
    pub fn check(&self, call: &ToolCall) -> Decision; // Allow | Ask(ApprovalRequest) | Deny(Reason)
}
```

- Инструменты и скоупы ребёнка берутся только из его контракта. Родитель может их сузить (`[calls.<имя>]` в своём
  контракте), но не расширить.
- `child.depth = parent.depth + 1 ≤ max_depth`.
- Бюджет: при вызове резервируется `min(лимиты ребёнка, остаток родителя)`; неистраченное возвращается после
  завершения. Резервировать нечего → `budget_exceeded` до запуска ребёнка. Так бюджет сессии — жёсткий потолок для
  всего дерева. Деньги и токены считаются отдельно: модели без цены участвуют только в токенных лимитах.
- Property-тест: никакая цепочка `derive_child` не даёт прав шире контракта и бюджета шире родительского.

### 5.3 Пути

- Корень — каталог проекта, выбранный при запуске. Вне корня — ничего и никогда.
- Hard-deny, не переопределяется: `.blind/**`, `.git/**`, `**/.env*`, `**/*.pem`, `**/*.key`, `**/id_rsa*`,
  `**/id_ed25519*`. Плюс `fs.deny` контракта.
- Доступ через `cap-std`: операции идут относительно дескриптора корня, `..` и симлинки наружу не выводят. Поверх —
  `globset` по нормализованному относительному пути; deny всегда побеждает allow.
- Лимиты: размер файла, число результатов `glob` и `grep`, отказ на бинарных файлах.

### 5.4 Запись только в копию

- Воркер с `fs.write` получает одноразовую копию рабочего дерева — снимок текущего состояния, включая незакоммиченные
  правки (например, `git worktree` от коммита `git stash create` плюс неотслеживаемые файлы скоупа; вне git — копия
  или reflink скоупа; детали — в M4). Писать, править и запускать `exec` он может только там.
- После `complete` харнесс считает diff копии с рабочим деревом, TUI показывает патч, человек применяет его целиком,
  по файлам или отклоняет. Применяет главный процесс, не агент.
- Параллельные воркеры дают независимые патчи; конфликт при применении показывается в TUI.
- Итог: ни один агент не пишет в рабочее дерево напрямую.

### 5.5 `exec`

- `exec { argv: [...] }`: argv должен совпасть с префиксом из allowlist контракта (`["cargo", "test"]`,
  `["clojure", "-M:test"]`), опционально с regex на остальные аргументы. Никакого `sh -c`; метасимволы shell не
  интерпретируются.
- Только в песочнице (§9): чтение — скоуп плюс пути тулчейна (`exec.read_extra`, например `~/.cargo`); запись — только
  копия воркера и его tmp; сеть запрещена; env пустой плюс allowlist (`PATH`, `LANG`, `HOME=<tmp>`); rlimits на CPU,
  память, число процессов и размер файлов; таймаут; лимит вывода.
- Если песочница на платформе недоступна, контракт с `exec` не загружается.

### 5.6 Одобрения

Политика на каждое действие: `allow`, `ask` или `deny`. Строгие умолчания:

| Действие | По умолчанию |
|---|---|
| вызов агента в пределах бюджета | allow |
| чтение в скоупе | allow |
| вызов MCP-инструмента из allowlist | allow; контракт может поставить `ask` |
| применение патча воркера | ask — всегда, не настраивается |
| `exec` | ask; контракт может разрешить `allow` для конкретного argv |
| всё, чего нет в гранте | deny — не настраивается |

### 5.7 MCP-инструменты для воркеров

```toml
# фрагмент agent.toml воркера
[mcp.tracker]
url   = "https://<адрес MCP-сервера>"          # HTTP: к серверу ходит главный процесс, адрес из allowlist
tools = ["search_issues", "get_issue"]        # allowlist: остальные инструменты сервера модель не увидит

[mcp.docs]
command = ["docs-mcp", "--root", "docs"]       # stdio: процесс запускается внутри песочницы воркера
tools   = ["search"]
env     = ["DOCS_TOKEN"]                       # явно переданные секреты; остальной env пустой
```

- Модели видны только инструменты из `tools`, под именами `mcp_<сервер>_<инструмент>`. Вызовы идут через тот же
  `grant.check`, одобрения, аудит и логи, что и встроенные инструменты.
- При одобрении контракта харнесс подключается к серверу, показывает описания и схемы разрешённых инструментов и
  закрепляет их хеш. Сервер поменял описание или схему → инструмент выключается до повторного одобрения: защита от
  подмены инструмента и от инъекций в описаниях.
- stdio-сервер запускается внутри песочницы воркера, как `exec`: env пустой плюс перечисленные секреты, сети нет.
  `network = true` — только явно и с пометкой на экране одобрения.
- К HTTP-серверу ходит главный процесс по адресу из allowlist; сам агент сеть не видит.
- Ответы MCP — недоверенные данные, как содержимое файлов.
- Координаторам MCP недоступен: у них по-прежнему только `agent_*`.

### 5.8 Внешний агент за MCP (`kind = "external"`)

```toml
# .blind/agents/ext-reviewer/agent.toml
name        = "ext-reviewer"
kind        = "external"
description = "Внешний ревьюер, выставленный как MCP-инструмент."
input       = "input.schema.json"
output      = "output.schema.json"

[external]
command = ["some-agent", "mcp", "serve"]   # stdio — в песочнице blind-exec; или url = "https://…" — через главный процесс
tool    = "review"                         # инструмент сервера, который и есть «агент»
network = true                             # внешнему агенту обычно нужен свой LLM; только явно, с пометкой при одобрении
env     = ["SOME_AGENT_API_KEY"]           # явно переданные секреты

[fs]
read = ["src/**"]                          # для stdio: что он видит на диске

[limits]
timeout   = "15m"
max_calls = 3                              # сколько раз за сессию его можно вызвать
retries   = 1                              # повтор при невалидном ответе
```

- Что агент делает внутри, харнесс не видит, поэтому строгость здесь — на границе: params проверяются до вызова,
  ответ — полной output-схемой после. Невалидный ответ → повтор ≤ `retries`, затем `failed(output_invalid)`.
- stdio-агент запускается в песочнице `blind-exec`: скоуп ФС из контракта, запись — только в копию (патч через
  одобрение, как у воркера), сеть — только при `network = true`.
- HTTP-агента вызывает главный процесс по адресу из allowlist; к нашей ФС у него доступа нет вовсе.
- Описание и схема инструмента закрепляются хешем, как в §5.7.
- Денежный бюджет не назначается — стоимость неизвестна; только таймаут, число вызовов и повторы.
- В дереве, на вкладке и на экране одобрения у такого агента метка `external`. Вместо транскрипта вкладка показывает
  запрос, ответ и MCP-уведомления о прогрессе.

### 5.9 Источники инструментов: AST, LSP, MCP (в обсуждении, 2026-11-21)

Два независимых слоя:

1. **Что доступно в проекте** — источники инструментов. Их можно добавить руками или харнесс находит сам.
2. **Кому это можно** — право в контракте агента. Найденный источник никому ничего не даёт, пока контракт его не
   перечислил.

| Источник | Что даёт агенту | Как появляется | Риск |
|---|---|---|---|
| AST (tree-sitter, внутри `blind-exec`) | структура файла, поиск по синтаксису | встроен; язык определяется по файлам | нет: только чтение, без внешних процессов |
| LSP (`rust-analyzer`, `gopls`, `clojure-lsp`…) | ошибки компиляции, переход к определению, поиск использований | харнесс находит по файлам проекта (`Cargo.toml`, `go.mod`…) и спрашивает один раз | сервер исполняет код проекта (сборочные скрипты) → только в песочнице, включение одобряет человек |
| MCP | инструменты сервера по allowlist (§5.7) | добавляет человек | как в §5.7 |

Автовключение делает источник доступным, но прав не выдаёт. Включение LSP и MCP — действие человека, пишется в аудит.

## 6. Архитектура

### 6.1 Процессы

```
┌──────────────────────────── blind (главный процесс) ────────────────────────────┐
│  TUI (ratatui) ◀── события ── Kernel ──▶ провайдеры (только адреса из конфига)   │
│   │ команды                     │  реестр контрактов · дерево задач              │
│   └────────────────────────────▶│  гранты · бюджеты · одобрения · аудит · логи   │
│                                 │  циклы агентов (по tokio-задаче на агента)     │
│                                 ▼                                                │
│          ToolBroker: grant.check → allow / ask / deny ──▶ HTTP MCP (allowlist)   │
└─────────────────────────────────┬────────────────────────────────────────────────┘
                                  │ stdin/stdout, JSON-кадры
                                  │ (по процессу на воркер с ФС, exec или stdio MCP)
┌─────────────────────────────────▼────────────────────────────────────────────────┐
│ blind-exec   [Seatbelt на macOS · Landlock + seccomp на Linux]                  │
│ ФС только в скоупе · запись только в копию · exec из allowlist · stdio MCP       │
│ без сети · без ключей провайдеров · пустой env                                   │
└──────────────────────────────────────────────────────────────────────────────────┘
```

- **Главный процесс:** TUI, ядро, провайдеры. Держит ключи провайдеров; ходит в сеть только к адресам из
  `providers.toml` и разрешённым HTTP MCP-серверам. Сам ФС-операций за агентов не делает, кроме применения
  одобренного патча.
- **`blind-exec`** — отдельный маленький бинарник без HTTP-клиента и TLS. По процессу на воркер-задачу с
  ФС-инструментами, `exec` или stdio MCP. Сначала включает ОС-песочницу под скоупы задачи, потом обслуживает запросы.
  Умирает вместе с пайпом (`PR_SET_PDEATHSIG` на Linux, EOF везде); на отмену — kill группы процессов.
- **У координаторов executor-а нет:** им нечего исполнять.

### 6.2 Цикл агента

```
1. запрос: system (заморожен) + tools (отсортированы) + messages (только дописываются)
2. стрим провайдера → нормализованные события: текст, reasoning, tool_call, usage, stop
3. stop:
   end_turn без complete  → напоминание харнесса, ≤ N раз, затем failed(no_complete)   (root: ход закончен, ждём человека)
   max_tokens             → один повтор с большим лимитом, затем failed(max_tokens)
   refusal                → инструменты этого хода не исполняются → failed(refusal)
   tool_use               → шаг 4
4. каждый вызов → grant.check: Allow | Ask (ждём человека) | Deny (blocked, is_error)
   разрешённые выполняются параллельно: agent_* → дочерние задачи; ФС, exec, stdio MCP → blind-exec; HTTP MCP → брокер
5. все результаты одним сообщением → шаг 1
6. complete(output): единственный вызов в ходе; полная схема ✓ → completed; ✗ → rejected (is_error), ≤ N раз → failed(output_invalid)
```

Лимиты (ходы, вызовы инструментов, токены, стоимость, время) проверяются на каждом шаге. Превышение → окончательное
состояние и каскадная отмена поддерева (`CancellationToken`-дерево повторяет дерево задач).

### 6.3 Вызов агента

- **Синхронный:** `agent_x(params)` держит ход родителя до результата ребёнка. Параллелизм — несколько вызовов в одном
  ходе, если модель это умеет (иначе по одному за ход); ограничено `max_parallel` родителя и глобальным
  `max_concurrent`.
- **Контекст ребёнка:** system = преамбула харнесса + `prompt.md`; первое сообщение = провалидированные params
  (+ `instructions`, если контракт разрешает). Транскрипт родителя ребёнок не видит.
- **Ребёнок может работать на другой модели и у другого провайдера**, чем родитель: связь между ними — только
  провалидированные JSON-данные.
- **Родитель получает только итог** (статусы совпадают по смыслу с agent-protocol):

```jsonc
{ "status": "completed", "task_id": "task_1a2b3c4d", "output": { "summary": "…", "findings": [] } }  // is_error: false
{ "status": "rejected", "errors": { "rubric": "missing required key" } }  // is_error: true; задача не создаётся, можно повторить
{ "status": "blocked", "reason": "unknown tool 'agent_ghost'", "available": ["clj-reviewer"] }
{ "status": "failed", "reason": "output_invalid" }  // так же: timed_out, cancelled, budget_exceeded
```

`rejected` по params никогда не создаёт задачу — инвариант из Go-версии.

### 6.4 Жизненный цикл задачи

```
params ✗ → rejected (задача не создаётся)
params ✓ → Running ─┬─ complete ✓ ───────────────────→ Completed
                    ├─ complete ✗ × N ───────────────→ Failed(output_invalid)
                    ├─ end_turn без complete × N ────→ Failed(no_complete)
                    ├─ refusal / ошибка провайдера ──→ Failed(refusal, provider)
                    ├─ таймаут ──────────────────────→ TimedOut        ┐
                    ├─ лимит бюджета ────────────────→ BudgetExceeded  │ поддерево
                    └─ отмена родителем / человеком ─→ Cancelled       ┘ отменяется
```

Окончательные состояния окончательны: повторный `complete` игнорируется и пишется в аудит (в Go-версии он
перезаписывал output).

### 6.5 Аудит, логи и хранение

- `<state>/sessions/<id>/` с правами 0700: `audit.jsonl` (каждая запись содержит хеш предыдущей; проверка —
  `blind audit verify`), `logs.jsonl` (§8.4), `transcripts/<task>.jsonl`, `patches/<task>.diff`.
- События аудита: `contract_loaded`, `contract_trusted`, `spawned`, `tool_call`, `allowed`, `asked`, `approved`,
  `denied`, `blocked`, `rejected`, `completed`, `failed`, `timed_out`, `cancelled`, `budget_exceeded`,
  `patch_applied`, `mcp_tool_changed`, `model_fallback`.
- Секреты не попадают никуда: ключи — `secrecy::SecretString`, логи маскируются до записи.

### 6.6 blind как MCP-сервер

- `blind mcp serve` — stdio-сервер. Внешний клиент (Claude Code, pi, opencode и другие) запускает его как свой
  MCP-сервер и видит одобренных агентов как инструменты `agent_<имя>` со схемами контрактов.
- Внешний клиент получает грант «внешнего root»: свой `can_call` и бюджет из `[mcp_server]` в `harness.toml`. Дальше —
  те же песочницы, лимиты, аудит и логи.
- Только stdio, без сети: дыр Go-прокси (п. 1–3 в §2.2) здесь нет по построению.
- Без TUI одобрения не ждут: `exec` с `ask` отклоняется, патчи копятся в `<state>/sessions/<id>/patches/` и
  применяются командой `blind patch apply`.

## 7. Модели и провайдеры

### 7.1 Принцип

Строгость живёт в харнессе. С какой бы моделью ни работал агент, исполняется только то, что прошло `grant.check` и
проверку полной схемой. Возможности провайдера (strict-схемы, параллельные вызовы, кэш) сокращают ретраи и
стоимость, но гарантию не дают.

### 7.2 Слой провайдеров

- Внутренний нейтральный формат: `Turn { role, blocks }`; блоки `Text`, `ToolCall { id, name, input }`,
  `ToolResult { id, content, is_error }`, `Reasoning(opaque)` — последний возвращается провайдеру как есть.
- `trait Provider { fn caps(&self, model) -> ModelCaps; async fn stream(&self, req) -> Stream<Event> }`. События
  нормализованы: `TextDelta`, `ToolCallStart` / `Delta` / `End`, `ReasoningDelta`, `Usage`, `Stop(reason)`.
- Адаптеры v1 (решение 2026-11-21: Anthropic не подключаем, первым идёт ollama.com):
  - `openai-compatible` — Chat Completions: OpenAI, OpenRouter, Gemini через его совместимый endpoint, облачный
    ollama.com, DeepSeek, Groq, Mistral, локальные Ollama, LM Studio, vLLM, llama.cpp;
  - `mock` — проигрывает сценарии для тестов.
- Позже: адаптер `anthropic` (Messages API), OpenAI Responses API, нативный Gemini, нативный API Ollama (`/api/chat`) — если через `/v1` чего-то не
  хватит.
- Модель в контракте — `провайдер/модель`, делится по первому `/` (так работают и id OpenRouter вроде
  `openrouter/vendor/model`).
- Конфиг провайдеров — только у пользователя, не в репо:

```toml
# ~/.config/blind/providers.toml
[defaults]
model = "anthropic/claude-opus-5-5"         # для импорта и мастера нового агента

[providers.anthropic]
kind    = "anthropic"
api_key = { env = "ANTHROPIC_API_KEY" }

[providers.openai]
kind     = "openai-compatible"
base_url = "https://api.openai.com/v1"
api_key  = { env = "OPENAI_API_KEY" }

[providers.openrouter]
kind     = "openai-compatible"
base_url = "https://openrouter.ai/api/v1"
api_key  = { keychain = "blind/openrouter" }

[providers.ollama-cloud]
kind     = "openai-compatible"
base_url = "https://ollama.com/v1"
api_key  = { env = "OLLAMA_API_KEY" }

[providers.ollama-cloud.models."gemma4:31b"]
tools          = true
parallel_tools = false
strict_schemas = false
usage          = true

[providers.local]
kind     = "openai-compatible"
base_url = "http://127.0.0.1:11434/v1"      # Ollama; так же LM Studio, vLLM, llama.cpp; ключ не нужен

[providers.local.models."qwen2.5-coder:14b"]
tools          = true
parallel_tools = false
strict_schemas = false
usage          = true
price          = { input = 0.0, output = 0.0 }   # $ за 1M токенов
```

**ollama.com** (облачные модели Ollama, корпоративный ключ) подключается через `openai-compatible` по
`https://ollama.com/v1`, ключ уходит как `Authorization: Bearer`. Что известно по документации Ollama на 2026-11-15:

- `tool_choice` не принимается — адаптер его и не отправляет (§7.5);
- облачные модели не поддерживают structured outputs → `strict_schemas = false`, схемы проверяет харнесс;
- `parallel_tool_calls` не документирован → считаем, что параллельных вызовов нет;
- usage в стриме есть (`stream_options.include_usage`) → токенные лимиты работают. Цены за токен нет, поэтому
  денежный бюджет таким агентам не назначается;
- имена моделей без суффикса `-cloud` (например, `gemma4:31b`); возможности у моделей разные, поэтому каждая модель
  описывается в `providers.toml` отдельно.

Ключи — только в env или Keychain, никогда в репозитории. Корпоративный ключ живёт только в главном процессе и
маскируется в логах, как и остальные (I12).

### 7.3 Возможности модели

| Возможность | Если есть | Если нет |
|---|---|---|
| tool calling | обычный режим | модель годится только для воркера без инструментов: output через JSON-режим, проверка схемой |
| строгие схемы инструментов | `strict` на `agent_*` и `complete`, схема понижается под профиль провайдера | схема уходит подсказкой, проверяет харнесс, ошибки → `rejected` и ретраи |
| параллельные вызовы | несколько `agent_*` за ход | по одному вызову за ход |
| кэш промпта | стабильный префикс; явные breakpoints, где они есть | — |
| reasoning | `reasoning` из контракта маппится на параметр провайдера; блоки возвращаются как есть | контракт с `reasoning` не загружается |
| usage в стриме | точный учёт токенов и денег | только лимиты ходов, вызовов и времени; денежный и токенный бюджеты не назначаются |

Возможности берутся из встроенной таблицы и переопределяются в `providers.toml` — у локальных серверов они сильно
различаются. Всё, что не подтверждено, считается отсутствующим.

### 7.4 Понижение схем

- Общий шаг для всех: объекты закрыты (`additionalProperties: false`) и в схеме для модели, и в полной схеме
  харнесса. Контракт, явно разрешивший лишние поля, не загружается.
- **Профиль Anthropic strict:** нет рекурсии, `minimum` / `maximum` / `multipleOf`, `minLength` / `maxLength`, сложных
  ограничений массивов → вырезаем из копии для модели, проверяем сами.
- **Профиль OpenAI strict:** все поля перечислены в `required`, необязательные выражаются через `null` в типе →
  понижатель переписывает схему, а харнесс перед проверкой полной схемой снимает `null` с изначально необязательных
  полей.
- **Без strict:** схема уходит как подсказка, проверяет только харнесс.
- Полная схема и все пониженные варианты входят в хеш контракта. Рекурсивная схема — ошибка загрузки.

### 7.5 Особенности адаптеров

**Anthropic:**

- `strict: true` на инструментах; `tool_choice` — только `auto` (принудительный выбор на Opus 5.5 и Sonnet 5.5
  возвращает 400), поэтому «обязан вызвать `complete`» обеспечивает цикл (§6.2);
- thinking-блоки возвращаются как есть, история только дописывается — иначе API отбросит или отклонит thinking;
- кэш: стабильный порядок tools → system → messages, breakpoint после system, контроль по
  `usage.cache_read_input_tokens`;
- `eager_input_streaming` только у `write_file` и `edit_file`: в этом режиме API не проверяет вход, это делает харнесс;
- `stop_reason: "refusal"` → инструменты хода не исполняются; server-side fallback на другую модель — опция контракта,
  пишется в аудит как `model_fallback`;
- `reasoning` → `output_config.effort`; мягкий бюджет — `output_config.task_budget` (beta).

**OpenAI-совместимые:**

- `tools` без `tool_choice`: `auto` и так значение по умолчанию, а часть провайдеров (например, ollama.com) это поле не
  принимает. `parallel_tool_calls` и `strict` у функций отправляются, только если возможность подтверждена в таблице;
- аргументы вызова приходят в стриме кусками (`delta.tool_calls[].function.arguments`) — собираются и парсятся
  строго, потом проверяются схемой;
- usage в стриме — через `stream_options.include_usage`;
- `reasoning` → `reasoning_effort`, если модель умеет;
- локальные серверы различаются: всё, что не подтверждено в `providers.toml`, считается отсутствующим.

### 7.6 Общее

- Ретраи 429, 5xx и обрывов — с backoff и `retry-after`, в пределах лимитов задачи.
- Сеть главного процесса — только к адресам из `providers.toml` и разрешённым HTTP MCP-серверам.
- Стоимость — `usage` × цены из `providers.toml`; цены меняются, в коде их нет.
- `MockProvider` проигрывает сценарии ходов. Те же сценарии гоняются с выключенными strict-схемами и параллельными
  вызовами — это доказывает, что строгость не зависит от провайдера (I16).

## 8. Интерфейс (TUI)

### 8.1 Раскладка

```
┌─────────────────────────┬────────────────────────────────────────────────────────────┐
│ AGENTS                  │  root   [ lead ⟳ ]   clj-reviewer ✓   approvals 1   logs   │
│ ▾ root            $0.42 ├────────────────────────────────────────────────────────────┤
│   ▾ lead   coord  ⟳     │ lead · coordinator · turn 7 · $0.21                        │
│     ✓ clj-reviewer      │ can_call: clj-reviewer, clj-test-writer                    │
│     ⟳ clj-test-writer   │                                                            │
│                         │ params  { files: [src/schema.clj], rubric: "…" }           │
│ WINDOWS                 │ → agent_clj-reviewer(files=[…])          ✓ 3 findings      │
│   approvals           1 │ → agent_clj-test-writer(namespace=…)     ⟳ turn 12         │
│   audit                 │                                                            │
│   logs                  ├─ logs · lead ──────────────────────────────────────────────┤
│   contracts             │ 12:03:11 INFO  tool_call  agent_clj-test-writer            │
│                         │ 12:03:12 WARN  rejected   output × 1 (test_count)          │
│ SESSIONS                │ 12:03:15 INFO  spawned    clj-test-writer · task_9f3e01ab  │
│   12:00 · active        │                                                            │
├─────────────────────────┴────────────────────────────────────────────────────────────┤
│ $0.61 / $5.00 · agents 4/32 · depth 2/3   Ctrl-X p jump · Ctrl-X commands · ? help     │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

- **Сайдбар** (по умолчанию слева):
  - `AGENTS` — дерево агентов текущей сессии со статусом и стоимостью;
  - `WINDOWS` — служебные окна: одобрения со счётчиком, аудит, логи, контракты, бюджет;
  - `SESSIONS` — прошлые сессии, только просмотр.
- **Вкладки** сверху: у каждого открытого агента и окна своя вкладка. `root` закреплён первым и не закрывается.
- **Основная область** — активная вкладка.
- **Лог-панель** снизу: логи активной вкладки (для агента — его поддерева); скрывается одной клавишей.
- **Статус-строка:** бюджет, число агентов, глубина, подсказки клавиш.

### 8.2 Вкладки

| Вкладка | Что внутри | Что можно сделать |
|---|---|---|
| `root` | чат с root: стрим ответа, вызовы агентов свёрнутыми строками | писать сообщения; `Enter` на вызове — вкладка этого агента |
| агент | заголовок (вид, модель, ход, стоимость, грант), params, транскрипт с вызовами инструментов, output | смотреть; отменить с поддеревом; открыть детей и родителя |
| `approvals` | очередь: патчи с diff, `exec` с argv, новые и изменённые контракты и MCP-инструменты | применить или отклонить, патч — по файлам |
| `audit` | события аудита | фильтры, поиск, переход к задаче |
| `logs` | все логи (§8.4) | фильтры, поиск, follow, переход к задаче |
| `contracts` | агенты, граф `can_call`, доверие, MCP-инструменты | одобрить; мастер нового агента; прямой запуск агента формой по его input-схеме |
| `budget` | стоимость и токены по агентам и сессии | — |
| `settings` | модели (root и по агентам), провайдеры и статус ключей, источники инструментов (§5.9), интерфейс | менять; всё пишется в те же файлы конфигов, их можно править и руками |

Вкладки саб-агентов — только для просмотра: человек пишет только в root, потому что канал к саб-агенту типизирован.
Вмешаться можно действиями: отменить, одобрить, отклонить.

### 8.3 Переключение между агентами и окнами

| Действие | По умолчанию |
|---|---|
| быстрый переход: fuzzy-поиск по агентам, окнам, сессиям | `Ctrl-X p` |
| команды: лидер-клавиша, после неё — подсказка со списком | `Ctrl-X` |
| вкладка по номеру / соседняя | `Ctrl-X 1…9` / `Ctrl-X [`, `Ctrl-X ]` |
| закрыть вкладку (кроме root) | `Ctrl-X w` |
| фокус в сайдбар и обратно / скрыть сайдбар | `Ctrl-X s` / `Ctrl-X S` |
| показать или скрыть лог-панель | `Ctrl-X l` |
| к следующему ожидающему одобрению | `Ctrl-X a` |
| отменить задачу с поддеревом | `Ctrl-X x`, с подтверждением |
| сменить пресет раскладки | `Ctrl-X v` |
| режим follow: фокус идёт за работающим агентом | `Ctrl-X f` |
| в транскрипте: открыть вызванного агента / вернуться к родителю | `Enter` на строке `agent_*` / `Backspace` |

- В сайдбаре стрелки и `Enter` открывают агента или окно во вкладке (или переключают на неё, если она уже открыта).
- **Вкладки открываются по мере вызовов.** Вызванный агент сразу получает вкладку — в фоне, справа от вкладки
  родителя; фокус остаётся, где был. Вкладки завершённых воркеров закрываются через `close_finished`. Если открыто
  больше `max_open`, новые агенты видны только в сайдбаре, а в полосе вкладок — счётчик `+N`.
- **Режим follow** (`Ctrl-X f`, по умолчанию выключен): фокус сам переходит на агента, который сейчас работает, и на
  новое одобрение.
- `Ctrl-B` и `Ctrl-A` по умолчанию свободны: это префиксы tmux и screen. `Ctrl-G` и `Ctrl-P` не используем: их перехватывает zellij (решение 2026-11-21). Всё переназначается в `ui.toml`.
- Мыши нет: навигация только клавишами (решение 2026-11-21). Сайдбар: `Ctrl-X s` — фокус, `↑` `↓` и `Enter` — открыть пункт.

### 8.4 Логи

- **Источники:** `harness` (внутренние события), `audit`, `agent` (ходы, вызовы, результаты инструментов), `exec`
  (stdout и stderr процессов), `provider` (модель, задержка, токены, стоимость, ретраи; тела запросов — только в
  debug), `mcp` (вызовы и ответы серверов).
- **Запись:** время, уровень, источник, агент и задача, сообщение, поля. Хранятся в
  `<state>/sessions/<id>/logs.jsonl`; в TUI — кольцевой буфер плюс догрузка из файла.
- **Вкладка `logs`:** все логи; фильтры по источнику, агенту (с поддеревом), уровню и тексту; режим follow; `Enter` —
  переход к задаче.
- **Лог-панель:** те же логи, автоматически отфильтрованные по активной вкладке.
- Секреты маскируются до записи.

### 8.5 Настройка

Настраивается в пределах: раскладка, секции, вкладки, клавиши, тема. Плагинов UI нет. UI-настройки только
пользовательские: на безопасность они не влияют, проект их не меняет.

```toml
# ~/.config/blind/ui.toml
[layout]
preset           = "default"    # default | focus (без сайдбара и логов) | monitor (большая лог-панель)
sidebar          = "left"       # left | right | hidden
sidebar_width    = 28
log_panel        = "bottom"     # bottom | hidden
log_panel_height = 8
startup_tabs     = ["root", "approvals"]

[sidebar]
sections = ["agents", "windows", "sessions"]   # порядок и видимость

[tabs]
auto_open      = "background"   # background — в фоне по мере вызовов | focus — сразу переходить | off — только сайдбар
show_cost      = true
close_finished = "5m"           # закрывать вкладки завершённых воркеров через N; "never" — не закрывать
max_open       = 12             # дальше новые агенты видны только в сайдбаре, в полосе вкладок — «+N»

[keys]
leader   = "ctrl-x"
switcher = "ctrl-x p"
# любое действие переназначается: <действие> = "<клавиши>"

[theme]
flavor = "mocha"                # Catppuccin: latte | frappe | macchiato | mocha (v1: только эти четыре)
```

### 8.6 Устройство

- Elm-архитектура: `AppState`, `Msg` (клавиши, события ядра, тики), `update(state, msg) -> Vec<Cmd>`,
  `view(&state, frame)`.
- Каждое действие пользователя — вариант `enum Action`; клавиши — таблица `клавиша → Action`, поэтому переназначение —
  это просто другая таблица.
- Раскладка считается из `ui.toml` через `Layout` ratatui; вкладки, сайдбар и лог-панель — свои виджеты.
- Ядро шлёт `KernelEvent` через `tokio::sync::broadcast`; TUI отправляет `KernelCommand` (`UserMessage`, `Approve`,
  `Deny`, `Cancel`, `TrustContract`, `RunAgent`). Модуль TUI не зависит от провайдеров, MCP и executor-а: интерфейс не
  может сходить в сеть или ФС.
- **Headless:** `blind run -p "<запрос>" --json` — то же ядро, события JSONL в stdout. Для CI и e2e.

## 9. ОС-песочница

**macOS:**

- Seatbelt-профиль генерируется на каждую задачу из её скоупов: `(deny default)`; `file-read*` — каталоги скоупа и
  системные пути для запуска бинарников; `file-write*` — только копия воркера и его tmp; `network*` — deny;
  `process-exec` — только бинарники из allowlist и stdio MCP-серверы контракта.
- `blind-exec` запускается через `/usr/bin/sandbox-exec -p <профиль>`. Риск: `sandbox-exec` помечен deprecated, хотя
  им пользуются действующие харнессы. Покрыть тестами на macOS-раннерах CI, чтобы заметить поломку.

**Linux:**

- `blind-exec` на старте: `PR_SET_NO_NEW_PRIVS` → Landlock (чтение и запись по каталогам скоупа; сеть — при ABI ≥ 4)
  → seccomp (запрет `socket` для `AF_INET` / `AF_INET6`, `ptrace`, `mount`, `bpf` и прочего) → опционально новые
  user- и net-namespace.
- Ядро без Landlock при `mode = "required"` → воркеры с ФС-инструментами, `exec` и stdio MCP не загружаются. При
  `mode = "degraded"` — только чтение через `cap-std`, без записи, `exec` и stdio MCP, с предупреждением в TUI.

**Обе платформы:**

- Landlock и Seatbelt работают по каталогам, глобы точнее, поэтому стен две: тонкая проверка в Rust и грубая в ОС.
- stdio MCP-серверы живут в той же песочнице, что и `exec`.
- Набор попыток побега (CI, обе ОС): чтение `~/.ssh` и файлов вне корня, запись вне копии, симлинк наружу, `..`,
  `connect()` наружу, форк-бомба, поиск ключей провайдеров в env, запись в `.blind/` и `.git/hooks`.
- Прецедент: Codex CLI (тоже Rust) использует ту же пару — Seatbelt на macOS, Landlock + seccomp на Linux. Изучить
  перед M6.

## 10. Rust

Структура и зависимости выбраны 2026-11-15; открытые вопросы — в §10.4.

### 10.1 Начать с трёх крейтов

```
blind/
├── Cargo.toml              # [workspace]
├── crates/
│   ├── blind-core/        # ЧИСТОЕ: типы, контракты, гранты и сужение, автомат задачи, бюджеты, исходы — без IO
```

### 10.2 Что хочется зафиксировать сразу

- Edition 2024, stable-тулчейн закреплён в `rust-toolchain.toml`.
- `#![forbid(unsafe_code)]` везде, кроме кода песочницы.
- Clippy с `-D warnings`; исходы — enum с исчерпывающим `match` (`clippy::wildcard_enum_match_arm` в ядре): добавил
  вариант — компилятор покажет все места, где его надо обработать.
- `thiserror` в библиотеках, `anyhow` в бинарниках.
- Newtype для имён и идентификаторов; у `Grant` нет публичного конструктора; `serde(deny_unknown_fields)` на конфигах.
- tokio; всё долгое отменяемо (`CancellationToken`-дерево).
- `tracing` в файл: терминал занят TUI.

## 11. Тестирование

- **Юнит:** ядро (сужение грантов, пути, понижение схем, автомат задачи, бюджеты) и загрузчик контрактов.
- **Property-based (`proptest`):** `derive_child` никогда не расширяет права; нормализатор путей никогда не выходит за
  корень; валидатор и загрузчик не паникуют на мусоре; отклонённый вызов не создаёт задачу.
- **Сценарии на `MockProvider`, без сети:** делегирование на три уровня; параллельные вызовы; rejected params →
  повтор; output rejected × N → failed; вызов несуществующего инструмента → blocked; `end_turn` без `complete`;
  `complete` координатора без детей; превышение бюджета → каскадная отмена; таймаут; отмена человеком; лимит глубины;
  родитель и ребёнок на разных провайдерах.
- **Независимость от провайдера:** те же сценарии с выключенными strict-схемами и параллельными вызовами (I16).
- **Провайдеры:** `wiremock` с записанными стримами Anthropic и OpenAI-совместимого API — обрывы, `max_tokens`, отказ,
  429 и 5xx, аргументы вызовов кусками; понижение схем под каждый профиль.
- **MCP:** mock MCP-сервер — инструмент вне allowlist не виден; изменённое описание → инструмент выключен;
  stdio-сервер не достаёт сеть и файлы вне скоупа; `blind mcp serve` уважает `can_call` и бюджет.
- **Песочница:** набор побегов из §9 на macOS и Linux в CI.
- **TUI:** снапшоты `insta` через `ratatui::backend::TestBackend` — пресеты раскладки, переключение вкладок, переход по
  `Ctrl-X p`, фильтры логов, переназначение клавиш.
- **Фаззинг (`cargo-fuzz`):** парсеры стримов, загрузчик контрактов, нормализатор путей.
- **Live-smoke** (только с `BLIND_LIVE=1`): реальная цепочка root → координатор → воркер на облачной и на локальной
  модели.
- **Покрытие (`cargo-llvm-cov`):** ядро ≥ 90%, остальное ≥ 80%; пороги только растут.

## 13. Модель угроз

| Угроза | Защита | Остаточный риск |
|---|---|---|
| агент вызывает то, чего нет в гранте | инструмента нет в запросе к модели; неизвестное имя → `blocked` | — |
| координатор «делает работу сам» | у него нет инструментов; `min_children`; output по схеме | может выдумать содержимое ответа — видно по дереву и аудиту |
| эскалация через ребёнка | нет регистрации в рантайме; права ребёнка ⊆ его контракта | человек одобрил слишком широкий контракт |
| агент правит правила или хуки | hard-deny на `.blind/**` и `.git/**`; запись только в копию; изменённый контракт требует одобрения | — |
| выход за корень (`..`, симлинки, абсолютные пути) | `cap-std` + глобы + ОС-песочница | ошибки ядра ОС |
| сеть и секреты через `exec` | песочница без сети, пустой env, allowlist argv, rlimits | устаревание `sandbox-exec`; на старых ядрах `exec` выключен |
| утечка ключей провайдеров | ключи только в главном процессе; executor — отдельный бинарник без HTTP-клиента | — |
| MCP-сервер подменил описание или схему инструмента | хеш описаний и схем закреплён при одобрении; изменение → инструмент выключен | вредный ответ в пределах разрешённого инструмента |
| stdio MCP-сервер как путь в ОС или сеть | запускается в песочнице воркера, без сети по умолчанию, env только с явными секретами | сервер с `network = true` |
| внешний клиент через `blind mcp serve` | только stdio; грант «внешнего root» с бюджетом и `can_call` | сам клиент не изолирован — это его зона |
| внешний агент за MCP делает что-то своё внутри | строгий вход и выход; stdio — в песочнице со скоупом контракта и явной сетью; HTTP — без доступа к нашей ФС; таймаут и лимит вызовов | внутреннее поведение вне нашего контроля — метка `external` в дереве, на вкладке и при одобрении |
| лавина агентов и счёт | `max_depth`, `max_agents_total`, `max_concurrent`, `max_parallel`, бюджеты с резервом | модель без usage — только лимиты ходов и времени |
| инъекция из прочитанных файлов и ответов MCP | радиус ограничен грантом; изменения — через человека | модель может ошибиться в пределах гранта |
| инъекция вверх по дереву | родитель видит только провалидированный output | строки output могут нести текст инъекции → enum и лимиты длины в схемах |
| данные уходят провайдеру | hard-deny секретов; локальные модели — данные не покидают машину | облачная модель видит всё, что прочитал агент |
| вредоносный репозиторий | контракты и `harness.toml` проекта не доверены до одобрения; доверие и провайдеры — вне репо | — |
| процессы-сироты | группа процессов на executor; kill при отмене; смерть при закрытии пайпа | — |

## 15. Критерии приёмки — инварианты строгости

| # | Инвариант | Чем доказывается |
|---|---|---|
| I1 | Исполняется только инструмент из гранта; любой другой вызов → `blocked`, не исполняется | сценарий + proptest на `grant.check` |
| I2 | У координатора и root нет инструментов, кроме `agent_*` (и `complete` у координатора) | тип `AgentKind` + тест загрузчика |
| I3 | Воркер не может вызвать агента | тип + тест загрузчика |
| I4 | Граф `can_call` ацикличен, глубина ≤ `max_depth` — статически и в рантайме | тест загрузчика + сценарий |
| I5 | Права ребёнка ⊆ контракт ∩ сужение; бюджет ребёнка ⊆ остаток родителя | proptest на `derive_child` |
| I6 | Нет доступа к ФС вне корня и в hard-deny; симлинки, `..`, абсолютные пути наружу не выводят | юнит-тесты + набор побегов |
| I7 | Невалидные params не создают задачу; невалидный output не доходит до родителя; родитель не видит транскрипт ребёнка | сценарии |
| I8 | Превышение лимита → окончательное состояние и отмена поддерева не дольше чем за 1 с | сценарий |
| I9 | `exec` только в песочнице, без сети и без секретов в env; без песочницы контракт с `exec` не загружается | набор побегов на обеих ОС |

## 17. Открытые вопросы

**Решено:** имя — `blind`; внешний агент за MCP — в v1 (§5.8); вкладки саб-агентов только для просмотра; вкладки
открываются по мере вызовов, в фоне; сплита в v1 нет; зависимости — §10.3; ollama.com — через `openai-compatible`
(§7.2); контракт в v1 — голый JSON (строгий профиль в Rust-типах), DSL отложен (§4.6); провайдер в v1 один —
`openai-compatible`, первым подключается ollama.com, адаптер Anthropic отложен.

**Основа:** всё строится из пар «агент + контракт», общего контракта нет; дерево — это сумма пар. В контракте только
то, что харнесс проверяет железно; `prompt`, `description` и `model` — уровень агента. Куда идёт работа, решает не
модель, а объявленные переходы и человек (§4.7). Доработок нет: ревью — отдельный шаг (человек или агент-ревьюер). Видов агентов три: `root`, `worker`, `external`;
`coordinator` убран.
Контракт output статичен: что нужно получателю, задаёт его input; компилятор проверяет, что output отправителя это
покрывает, а харнесс передаёт получателю только объявленные им поля.

Минимальный состав — root и один воркер; без воркеров root просто разговаривает. Отдельной проверки готовности на
старте нет: недоступного воркера (контракт не одобрен или изменён, нет ключа модели) сборщик цепочки показывает серым
с причиной.

Веб-поиск у root — настройка `allow`, `ask` или `off`, по умолчанию `ask`: каждый запрос сначала показывается
человеку в TUI. Root читает проект, и без этого код мог бы утечь через поисковый запрос (секреты и так закрыты
hard-deny). Каждый ушедший запрос пишется в аудит.

1. Строгое разделение coordinator / worker / external, без смешанных агентов — ок?
2. Root совсем без чтения файлов (контекст только через воркеров вроде `explorer`) — или дать root read-only?
3. Запись только через патч на одобрение — или нужен режим прямой записи?
4. Свободный текст от родителя к ребёнку (`instructions`): по флагу контракта, как сейчас, или только
   типизированные params?
5. Внешние CLI-воркеры (`claude`, `pi`) нужны в v1, или хватит внешнего агента за MCP?

Вопросы по Rust — в §10.4.
